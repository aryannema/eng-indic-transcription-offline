Transcription Without A GPU

Hindi and seven other Indian languages, transcribed on an ordinary CPU at fourteen times faster than the audio plays — on one core. No graphics card, no CUDA, no network. Every number below came off our own hardware.

The assumption that speech recognition needs a GPU comes from the models most people meet first. Whisper is 1.5 billion parameters. Sarvam's Saaras uses a 3B decoder. Bodhan's Indic-Transcribe is 1.2B and takes 85 seconds to transcribe 20 seconds of audio on a CPU — measured, and comfortably unusable.

This uses a different model: AI4Bharat's Indic Conformer, quantised to 8-bit integers, 197 MB on disk. It is smaller because it does one job — turn speech into text in a known language — rather than translating, summarising and answering questions about it.

The red line is real time — audio playing at normal speed. Everything is far to the right of it, and the single-threaded case is the one that matters: 45 seconds of speech decoded in 3.2 seconds on one core.

Threads help, and they help less than you would expect. Going from one core to eight buys 2.7×, not 8×. So this is not a machine that needs many cores — it needs a core.

Memory is flat at 744 MB regardless of thread count, because the weights are loaded once and shared.

That is a specification most machines built since roughly 2012 already meet. It also means a Raspberry Pi 4, a low-end office desktop, or a VPS with no accelerator.

The honest caveat: those numbers came from a workstation CPU and from an Intel Arc laptop. The single-thread figure is the reliable one to reason from, because it is the case with the least hardware advantage — a slower core will be slower proportionally, and there is a lot of headroom between 14× and 1×.

How it works

audio file or microphone
        │
        ▼
16 kHz · mono · float32 · [-1.0, 1.0]      the contract every ASR model expects
        │
        ▼
80-dim log-mel features, 100 frames per second
        │
        ▼
Conformer encoder  24 layers · 1024 dims · the 197 MB
        │                    100 frames/sec in → ~12.5 vectors/sec out
        ▼
CTC decoder       one matrix multiply · 5,633 tokens
        │
        ▼
collapse repeats → text

The decoder is the surprising part. It is two operations — a matrix multiply and an addition — projecting 1024 dimensions onto a 5,633-token vocabulary, once per frame, with nothing carried between frames. That statelessness is why it is fast and why it fits.

The catch, stated plainly

No language model means no self-correction

Each frame is decided independently. There is nothing in the decoder that knows फ्रेशर is a word and ेशर is not, so under noise it drops a syllable and has no way to recover.

Larger attention-based models re-read the whole clip and fix earlier words using later audio. That is why they are more accurate, and it is also exactly why they cannot run in 197 MB on one core. This is the trade, not a defect.

English words come out in Devanagari

The vocabulary is 5,633 tokens and all of them are Indic script. The word upload has no representation in it, so the model writes अपलोड. That is an arithmetic limit, not a quality one — no amount of tuning fixes it without rebuilding the vocabulary.

For a Hindi transcript this is usually correct behaviour. For code-switched dictation it is not what you want, and the model that does it properly needs roughly 3 GB of video memory.

Languages

Eight, in one 197 MB file. Declare one at setup.

as  Assamese      bn  Bengali       brx Bodo         gu  Gujarati
hi  Hindi         kn  Kannada       ks  Kashmiri     mr  Marathi

Hindi and Urdu cannot both be enabled

They are near-identical in sound and differ mainly in script. Asked to choose, a model silently writes the wrong script rather than raising an error — we reproduced exactly that, getting Arabic script out of Hindi audio.

Declaring the language at setup removes the model's weakest decision. Wispr Flow's own documentation gives users the same advice, and they have a cloud model covering a hundred languages.

Running it

# sherpa-onnx wheels lag new Python releases — pin 3.12
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python sherpa-onnx numpy

python scripts/fetch_models.py --indic hi
python scripts/transcribe.py recording.wav

Input must be 16 kHz mono. Anything else converts in one command: 

ffmpeg -i input.mp3 -vn -ac 1 -ar 16000 out.wav
#              -vn drop video  -ac 1 mono  -ar 16000 resample

Verify the privacy claim yourself

Nothing here is a promise. Run this while transcribing and count the packets: 

sudo tcpdump -i any port not 22

What this is not

Not live captioning. It transcribes a recording or a completed utterance. Word-by-word streaming needs a cache-aware encoder, and no such model has been published for any Indian language.

Not speaker separation. Diarization is a separate model — about 35 MB, and roughly six times the processing cost of the transcription itself.

Not mixed-script output. See above. That needs roughly 3 GB of VRAM and a different model.
